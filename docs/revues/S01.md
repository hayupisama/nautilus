# Revue du sprint S01

Période : 20 et 21 novembre 2026. Mode local, sans infrastructure (VPS reporté).
Objectif : contrat d'API v0.2.0, base du design system accessible, squelette de l'API.

## Ce qui est livré

- **Contrat d'API v0.2.0** : couvre tout le lot 0 (profil du compte connecté, réservations du passager et du chauffeur, liste des courses côté administration). Le contrat est validé automatiquement, et les clients Dart et TypeScript sont produits à chaque version taguée. La procédure de montée de version est documentée.
- **Design system accessible (package commun)** : thèmes clair, sombre et contraste élevé, bouton accessible. Chaque composant est testé avec les règles d'accessibilité (50 tests, couverture complète du design system). Contrastes au-delà de 7:1, cibles tactiles d'au moins 48 dp.
- **Squelette de l'API** : architecture hexagonale par module, règle d'architecture vérifiée par un test, interfaces REST générées depuis le contrat v0.2.0, tests et build JVM dans l'intégration continue (23 tests).
- Les deux fonctionnalités « socle » du contrat et de l'API sont terminées.

## Comment le tester

- **Contrat** : dans le dépôt du contrat, lancer le lint et la vérification de génération (`npm run lint`, `npm run generate:check`). Les deux doivent passer sans erreur.
- **Design system** : dans le package commun, lancer `flutter test`. Les tests de widgets vérifient l'accessibilité des thèmes et du bouton.
- **API** : dans le dépôt de l'API, lancer `./mvnw verify` (tests dont architecture, et build JVM). Docker Desktop doit être démarré pour les tests avec base de données.
- Aucune recette déployée : rien à tester sur un environnement distant à ce stade.

## Ce qui reste / risques

- **Infrastructure VPS** (base PostgreSQL et PostGIS, Keycloak, déploiement) : reportée par ta décision. Rien n'est déployé.
- **Suite du lot 0** : le client Dart généré pour l'appli mobile, la connexion Keycloak, les composants de saisie (champ, carte, étape) et le sélecteur sont prévus au sprint suivant.
- **Dette technique** : la protection des versions taguées du contrat (que tu as validée pour maintenant) est encore à appliquer en début de sprint suivant. Quelques points de qualité sont suivis sans bloquer (tests de non-régression d'accessibilité, couverture de l'API, mises à jour mineures de paquets).
- **Estimation** : le composant « design system » était engagé à 3 h, alors que le cahier le chiffre à 6 h. Il a pris 1 h 45 réelle. À vérifier avant de planifier la suite.
- **Capacité** : 13 h ont été engagées pour 10 h disponibles. 7 h réelles ont été consommées.
- **Réglage** : la durée maximale de session était réglée à 1 minute, ce qui a fait perdre une session. À corriger de ton côté.
